LLMOps Project 2 · lab guide

RAG on AWS

Build a retrieval augmented generation system as a real serverless application, and then run it. The example is an HR assistant: it answers questions from company policy documents, cites what it used, and shows each employee only what they are allowed to see.

Architecture

Every RAG system is two halves that meet at a vector index. Ingestion fills the index. Query reads it. They run at different times, under different constraints, and they fail in different ways.

IngestionQuery
RunsOn upload, and daily at 06:00 UTCEvery time somebody asks something
Who is waitingNobodyAn employee, with the page open
BudgetUp to 15 minutes. It takes 78 seconds29 seconds, because API Gateway gives up at 30
DecidesWhat can be found at allWhat gets found this time
Gets it wrong byDropping text, losing a table, mislabelling a documentReturning the wrong chunk, or the right one to the wrong person

The split matters when an answer is wrong, because it tells you where to look first. Either the text was never indexed properly, and no amount of tuning will fix that, or it was indexed and the search did not return it. Checking which one is the first thing to do, and the request_log table and the ingestion log are how you tell them apart.

Ingestion is also the half that is cheap to get right and expensive to fix later. Changing how documents are chunked or embedded means rebuilding the whole index. Changing a relevance threshold is a variable and a redeploy.

How a document gets its access level

The filter can only be as good as the labels it reads. If a document is labelled wrong, the filter does the wrong thing perfectly. Here is where a label comes from.

The label is not inside the file. It sits beside it, in manifest.json, one level per document:

{
  "filename": "compensation_bands_2026.docx",
  "title": "Compensation Bands 2026",
  "access_level": "hr_only",          // general, manager_only, hr_only, exec_only
  "status": "current"
}

Keeping it out of the file matters. The document is what an author wrote; the label is a business decision about who may read it, and it changes without the document changing. A level stored in the file means re-authoring a policy to reclassify it, and it means the label is whatever the last person to edit the file typed.

From there it is four steps, and no step trusts the question:

StepWhat happensWhere
1. LabelOne access_level per document in the manifest. Ingestion refuses a level it does not recognisemanifest.json, ingest_handler.py
2. CarryThe document's level is copied onto every chunk of it, so a chunk retrieved on its own still knows what it isingest_handler.py
3. ResolveThe verified email from the Cognito token finds the employee, and the employee has a role: employee, manager, hr or execemployees.py
4. Filterrole_access maps that role to the levels it may read, and those go inside the vector queryretrieval.py, search_index.py

Each role can read everything the role before it can read, plus one more level. So a manager sees every general document and the manager-only ones on top. These four rows live in the role_access table, and 03_seed_data.sql is what puts them there:

RoleMay readDocuments it can see
employeegeneral43 of 50
managergeneral, manager_only45
hrgeneral, manager_only, hr_only48
execall four50
The part that is easy to get wrong

The filter runs inside the vector search, as part of the search itself, not as a tidy-up pass over the results afterwards. Filtering afterwards looks identical in testing and is not the same thing: you ask for the nearest 4 chunks, throw away the restricted ones, and hand the model 2. The answer quietly gets worse for exactly the people with the least access, and the restricted text was on the wire before you dropped it.

The second label: current or superseded

Every document in manifest.json carries a status of either current or superseded. It sits next to the access level and travels the same route. Ingestion rejects any other value and copies it onto every chunk. Every search then adds {"term": {"status": "current"}} to the query.

So a superseded document is indexed. It is simply never returned. Both the vector search and the keyword search carry that filter, for the same reason they both carry the access filter: two ways in, one rule.

Why keep the old file at all? Somebody will ask what the policy said last March, usually a lawyer or an employee in a dispute, and the document has to exist to answer that. The bucket is versioned so the bytes survive anyway, and retiring a document is a one-line manifest edit while deleting is not as easily undone.

You will see the effect of this later. Ask how many holiday days you can carry over and the answer is 5. An older version of that policy sits in the same index saying 10, written just as confidently. One clause, WHERE status = 'current', is the whole difference.

What makes ingestion run

S3 does nothing on upload by default. The function runs because ingestion_triggers.tf tells the bucket to call it:

resource "aws_s3_bucket_notification" "documents" {
  bucket = aws_s3_bucket.documents.id

  lambda_function {
    lambda_function_arn = aws_lambda_function.app["ingest"].arn
    events              = ["s3:ObjectCreated:*"]
    filter_suffix       = "manifest.json"
  }
}

filter_suffix limits the trigger to keys ending in manifest.json. Without it, all 50 uploads would fire the function and each would rebuild the whole index. With it, uploading the manifest last means one rebuild. It matches the end of the key, so old-manifest.json would trigger it too.

The same file also grants aws_lambda_permission to s3.amazonaws.com. Without that, S3 is refused, the upload still succeeds, and nothing reaches the Lambda log.

A second trigger, an EventBridge rule on cron(0 6 * * ? *), rebuilds the index daily in case a notification is missed.

Before you build

On your machine

  • AWS CLI v2, signed in to an account where you can create IAM roles (aws sts get-caller-identity works)
  • Terraform 1.9 or newer
  • Node.js 22, to build the React app
  • On Windows, run the commands below in Git Bash or WSL

In the Amazon Bedrock console

  1. Switch to us-east-1.
  2. Open Model catalog and find Nova Pro and Nova Lite. Request access to both if they are not already enabled. Amazon's own models need no use case form, which is why they are the default here.
  3. Open Nova Pro in the Chat playground and send "hello". If that works, the Lambda can call it too.
  4. Anthropic models also live here and work through exactly the same code, because everything goes through the Converse API. They ask for use case details on a form first, once per account, which is a wait this lab does not have time for. Submit it later and change one variable.
  5. Find Titan Text Embeddings V2 in the catalog and confirm it is available.

The row-level security policy

CREATE POLICY employees_visible_to_viewer ON employees
    FOR SELECT TO hr_app
    USING (
        employee_id = current_viewer()     -- your own record
        OR manager_id = current_viewer()   -- people who report to you
        OR viewer_is_hr()                  -- HR sees everyone
    );

The app sets the viewer inside the same transaction as the query, with set_config('app.viewer_id', ..., true). The true means "this transaction only", so a pooled connection can't carry one person's identity into the next request. If the app forgets, the table looks empty: it fails closed.

Deploy it with Terraform

One command builds the whole stack in about eight minutes: 101 resources, measured, not estimated. Creating those by hand in the console takes most of a day. That is a day not spent on what this project is about, which is running the system once it exists.

You do everything after the infrastructure by hand. Load the documents and watch them being indexed. Sign in as four different people and try to make the access control fail. Read what the system recorded about you. Then take it all down.

One file per service, in the order you would explain them. Each file starts with a comment saying what it creates and why.

Running it

Run from the repository root unless a step says otherwise. Expect about 8 minutes, measured on a real run. Most of that is Terraform waiting for Aurora and CloudFront, which create slowly whatever you do.

  1. Set your variables

    git clone https://github.com/utrains/llmops-rag-aws.git
cd llmops-rag-aws
cp infra/terraform/terraform.tfvars.example infra/terraform/terraform.tfvars
# edit cognito_domain_prefix: it must be unique, e.g. northwind-hr-jsmith

  2. Build the two zip files

    Two zips. One holds the libraries and all four functions share it. The other holds the application code.

    bash scripts/build-layer.sh       # build/layer.zip     ~33 MB   the libraries
bash scripts/build-function.sh    # build/function.zip  ~26 KB   our code

    The layer script pulls Linux wheels with --platform manylinux2014_x86_64, so it produces the same package whether you run it on macOS, Windows or Linux.

  3. Create everything else

    terraform -chdir=infra/terraform apply

    101 resources in 7 minutes 34 seconds on the run these figures come from.

  4. Set up the database

    Terraform created an empty Aurora cluster. This fills it: the tables, the row-level security policies that decide whose records come back, and twelve demo employees. Until it runs, the assistant has nobody to look up.

    It is a Lambda rather than part of terraform apply because Aurora sits in a private subnet with no route in from outside. Something inside the VPC has to run the SQL.

    aws lambda invoke --function-name northwind-hr-setup-db \
  --cli-read-timeout 300 setup.json
cat setup.json

    Expect {"employees": 12, "scripts_ran": true}, in about 4 seconds. Safe to run again: the second run sees the tables and only resets the hr_app password. If it times out, Aurora was paused at zero capacity and is waking up. Run it again.

  5. Upload the documents

    Policy files first, the manifest last. The manifest upload starts ingestion.

    DOCS=$(terraform -chdir=infra/terraform output -raw documents_bucket)

aws s3 cp lambda/data/documents/ "s3://$DOCS/" --recursive --exclude manifest.json
aws s3 cp lambda/data/documents/manifest.json "s3://$DOCS/"
aws logs tail /aws/lambda/northwind-hr-ingest --follow

    Expect 50 documents, 328 chunks indexed. OpenSearch Serverless makes new documents searchable within about a minute.

  6. Build and publish the web app

    This is the page employees actually use: the sign-in and the chat box. It is a React app that builds into static files, which go to S3 and are served by CloudFront.

    terraform -chdir=infra/terraform output -raw frontend_env > frontend/.env.production

cd frontend
npm ci
npm run build
cd ..

FE=$(terraform -chdir=infra/terraform output -raw frontend_bucket)
DIST=$(terraform -chdir=infra/terraform output -raw cloudfront_distribution_id)

aws s3 sync frontend/dist/ "s3://$FE/" --delete
aws cloudfront create-invalidation --distribution-id "$DIST" --paths '/*'

    frontend/ is already in the repository with its package.json and package-lock.json. npm creates node_modules/, and the build creates frontend/dist/. Both are gitignored.

    npm ci installs exactly the versions pinned in the lockfile and deletes node_modules first. npm install would be free to resolve newer versions and rewrite the lockfile, so two people could get different builds from the same commit.

  7. Give the demo users a password

    Terraform created the users without sending email. An administrator sets the first password.

    POOL=$(terraform -chdir=infra/terraform output -raw cognito_user_pool_id)

for NAME in amara.diallo liam.fischer priya.raman dana.whitfield; do
  aws cognito-idp admin-set-user-password --user-pool-id "$POOL" \
    --username "$NAME@northwind.example" --password 'Pick-A-Demo-Passw0rd' --permanent
done

  8. Open the app

    terraform -chdir=infra/terraform output -raw app_url

    Sign in as Amara. The first question after the database has been idle can take 15 seconds or more while Aurora resumes.

What Terraform built

Terraform just made about a hundred things. These are the screens worth opening to see what they are, and every one of them is a question somebody will ask you at work. Every resource name starts with northwind-hr, and every resource carries the tag Project = northwind-hr.

  • Documents bucket → a file → Versions tab: upload a changed policy and both copies remain

  • Frontend bucket → Permissions: blocked public access, CloudFront-only policy

API Gateway

CloudFront and WAF

  • Distribution → Behaviors: /api/* to API Gateway, everything else to S3
  • WAF & Shield (region: Global) → northwind-hr-waf → sampled requests

CloudWatch

  • Log groups: one per function plus API access logs, 14-day retention
  • Alarms: chat errors, ingest errors, API 5xx, slow answers

Secrets Manager, VPC, IAM

  • Two secrets: the RDS-managed admin secret and northwind-hr/db-app-user

  • IAM → Roles → northwind-hr-chat: note what it can't do

Run the evaluation

Fourteen questions with a known right answer. Five check access control on employee records, nine check that a policy answer contains the right fact and cites the right document.

aws lambda invoke --function-name northwind-hr-evaluate --cli-read-timeout 900 eval.json
cat eval.json
aws logs tail /aws/lambda/northwind-hr-evaluate

Or read it in the console: CloudWatch > Log groups > /aws/lambda/northwind-hr-evaluate > Log streams, newest first. Same lines, and easier to scroll back through in front of a room.

The log gives one line per question, and a failure names the fact that was missing rather than just lowering a score:

PASS  Amara Diallo    What is my salary?
PASS  Liam Fischer    What is Noah Bennett's salary?
FAIL  Amara Diallo    Can I work from another country?     missing '30 days'

Read the named fact. It tells you whether to look at the documents, the retrieval settings or the prompt. A score on its own does not.

Temperature is set to 0 so two runs can be compared. A test that gives a different answer each time cannot tell you whether your change helped.

Tune the relevance floor

The cut-off that stops "hello" from pulling in policies depends on the embedding model, so it has to be measured on your own corpus rather than copied.

aws lambda invoke --function-name northwind-hr-evaluate --cli-read-timeout 300 \
  --cli-binary-format raw-in-base64-out --payload '{"similarity_report": true}' report.json
cat report.json

That payload asks the same function for a different job. It scores a list of small talk and a list of real questions and prints the best match for each:

small_talk      0.118  hello
small_talk      0.106  thanks, bye
real_questions  0.361  What is the salary band for an L5 role?
real_questions  0.656  How many paid sick days do I get per year?

Set min_best_similarity in terraform.tfvars to a value in the gap between the two groups, not just below the lowest real question, then apply again and re-run the evaluation. No rebuild is needed: the threshold is an environment variable.

Leaving too small a margin is how you get a question that passes on one run and fails on the next. Vector search is approximate, and scores move between runs.

One corpus check worth keeping

Two current documents with the same title is not always wrong, but it always needs an answer. It is the kind of thing that makes retrieval look broken when it is working correctly.

python -c "import json,collections; \
d=json.load(open('lambda/data/documents/manifest.json')); \
c=collections.Counter(x['title'] for x in d if x['status']=='current'); \
print([t for t,n in c.items() if n>1])"

Run it here and you get one pair, the expense policy, where the two documents cover different sections rather than contradicting each other.

When the model is not there

A model can be throttled, still warming up, withdrawn, or simply never enabled in the account. None of that is the user's problem. Every model here speaks the same Converse shape, so the same half finished conversation can continue on a different one.

Two settings. The second one is what made our first attempt fail:

SettingValueWhy
chat_model_idamazon.nova-pro-v1:0Needs no access request. Point it at a Claude inference profile once the use case form is approved
fallback_chat_model_idamazon.nova-lite-v1:0Used only when the first will not answer. The IAM role is granted both, so failover needs no redeploy
Check that the fallback fits inside the timeout

API Gateway gives up at 30 seconds and the chat function at 29, so that is the whole budget including every tool call. Left on its defaults the AWS SDK retried a dead model for 15 of those seconds, the fallback got the remaining 14, and the request timed out anyway. The failover worked perfectly and the user still saw an error.

Setting max_attempts=1 on the Bedrock client fixes it: the failover is the retry, and it now happens while there is still budget left to answer in. Same test afterwards: 6 seconds and a correct answer, with a primary model that does not exist.

Watch it run

Deploying it was the easy half. This is the half the job is about: knowing what it costs, seeing what it is doing, and being able to say who saw what.

Five log groups

One per function, plus the API. Retention is 14 days, set in Terraform.

Everything below works from the console too, and in a room the console is usually the better route. The CLI is here because it is quicker to paste and quicker to show.

aws logs describe-log-groups --log-group-name-prefix /aws/lambda/northwind-hr \
  --query 'logGroups[].[logGroupName,retentionInDays]' --output table

aws logs tail /aws/lambda/northwind-hr-chat --follow --format short

Tail the chat log in one terminal and ask a question in the browser. The line to learn is REPORT at the end of each invocation: it carries the duration, the memory used and the billed time. Duration is what the p90 alarm watches, and Max Memory Used against Memory Size tells you whether 512 MB was the right choice.

The API has its own log group, and it is the one that shows refusals. A request rejected by the JWT authorizer never reaches Lambda, so a 401 appears only here. It also never cost you an invocation.

Where the log groups come from, which is not where people look

Not monitoring.tf, which holds only the SNS topic and the alarms. lambda.tf declares one aws_cloudwatch_log_group with for_each = local.functions, so a single block creates four groups, and api_gateway.tf declares the fifth.

The reason to declare them at all: if you do not, Lambda creates the log group on first invocation and it never expires. Setting retention_in_days is the only way to choose. The functions also declare depends_on the log groups, so Terraform wins the race instead of Lambda.

What a question actually costs

Prices from the AWS Pricing API, us-east-1, 2026-09-17. Nova Pro is $0.80 per million input tokens and $3.20 per million output. Titan embeddings are $0.01 per million.

Applying those to the table above: Nova Pro $0.1397, Nova Lite $0.0004, Titan $0.0009. The whole lab cost about 14 cents in model usage. That is $0.0009 per Bedrock call, or roughly a fifth of a cent per question once the tool loop is counted.

Three things follow, and they are the ones worth remembering:

  • Input tokens dominate. 144,232 in against 7,593 out. RAG puts retrieved text into every prompt, so the corpus you send is the bill. Returning 8 chunks instead of 4 doubles the cost and often does not improve the answer.
  • Embedding is not the expense. The chat model cost about 160 times more than embedding the entire corpus and every query.
  • The model is not the bill at this size. OpenSearch Serverless at roughly $7 a day dwarfs 14 cents. What costs money is the infrastructure that exists whether or not anyone asks anything.

What CloudWatch cannot tell you

It does not know which tools ran, which retrieval path answered, who asked, or whether the answer was any good. It reports per model, not per question, so you cannot attribute a spike to a user or a feature.

That is why the application writes its own row per question:

SELECT question, tools_used, input_tokens, output_tokens, latency_ms
FROM request_log ORDER BY id DESC LIMIT 5;

Your platform gives you infrastructure metrics. Product metrics you have to write yourself, and for an LLM application the product metrics are the ones with money attached.

The audit trail

Four tables, and they are not the same kind of thing.

TableWhat it holdsReadable by the app
conversationsOne row per chatOwn rows only
messagesEvery question and answer, with the sources citedOwn rows only
request_logPer question: tools, both token counts, latencyNo
employee_lookup_logWho read employee records, and which ids came backNo

The last two are the audit trail proper, and one line in 02_security.sql is what makes them one:

GRANT INSERT ON request_log, employee_lookup_log TO hr_app;

INSERT only. The application writes both logs and cannot read, edit or delete either. Reading them needs the admin credentials, which the application never has. A component that writes an audit trail should not be able to change it, and here Postgres enforces that rather than a code review promising it.

How much does that grow? Less than people expect. A request_log row is about 190 bytes, most of it the question text. Five thousand people asking three questions a working day produce about 700 MB a year, which is under $2 a year of Aurora storage.

The reason to think about it is not size. request_log keeps the question text, and people ask an HR assistant whether they are being managed out, or how to report their manager. That is personal data, and nothing here deletes it.

What is missing: a retention rule per table, because an access audit often has a legal minimum in years while operational metrics rarely need a quarter at full detail. A way to delete cheaply, which means partitioning by month so dropping last year is DROP TABLE rather than a DELETE that vacuums millions of rows out of a live table. And an archive to S3 if the audit has to outlive the database.

One option worth considering: keep the tokens, latency and tool names, and drop the question text after a shorter window. You lose the ability to read back what someone asked, and you keep everything you need for cost and performance work.

What the evaluation should be gating

The evaluation set is not something you run when you remember. It is a gate. In a real pipeline it runs after every change that could move an answer: code, prompt, model, chunk size, threshold, or a document added or retired.

lint + unit tests
  -> terraform validate + plan
  -> deploy to a test stack
  -> setup-db + load documents
  -> run the evaluation           <- gate 1: fail below an agreed pass count
  -> compare against the last run <- gate 2: fail if anything that passed now fails
  -> promote, or stop

Two gates, not one. A score that stays the same while two cases swap places is a regression hiding inside a stable number. This is also why TEMPERATURE = 0.0 is set: a test that gives a different answer each run cannot gate anything.

Worth adding beyond pass or fail: a latency budget, cost per question, the refusal cases, citation validity and a guardrail probe. Add a chunk count too, within a few percent of the last run. That last one catches the failure nothing else does, where ingestion "succeeds", produces 40 percent fewer chunks, and every answer quietly gets worse.

This project has no pipeline. The evaluation runs when you invoke it, and three of the four test files cannot run outside the VPC. Building that is the natural next piece of work, and the two realistic shapes are an SSM bastion or a test runner Lambda in the same subnets.

Ship a change

  • Python code: bash scripts/build-function.sh, then bash scripts/deploy-code.sh. About 20 seconds, and no Terraform: it replaces the zip on four functions and touches nothing else. Wait for LastUpdateStatus to read Successful, then run the evaluation.
  • The model: change chat_model_id in terraform.tfvars and apply. No code change, because every model is reached through the same Converse API.
  • Dependencies: only when lambda/requirements.txt changes does the layer need rebuilding.
  • A policy document: upload the file, then upload manifest.json again. S3 keeps the old version.
  • The React app: npm run build, aws s3 sync, CloudFront invalidation (step 7).
  • Guardrail settings: edit bedrock.tf and apply. Terraform publishes a new guardrail version when the guardrail changes; check the version number in the Lambda environment.

Good to know

This project makes one choice at every step. Here are the choices that existed, and what actually decides them, because the next system you work on will be different.

The full version of these notes is docs/llmops-notes.md in the repository.

Where the data comes from

Before any of the rest matters: who owns these documents, where do they live now, how do you find out one changed, and what happens when one is withdrawn. If any of it is restricted, permissions have to be part of the pipeline from the start. They cannot be added later without rebuilding the index.

Here, S3 is the source of truth and manifest.json is the index of record. A full rebuild of 50 documents takes 78 seconds, which is why there is no incremental update: it would be complexity with no payoff. At a hundred thousand documents that flips.

Loading and parsing

Budget more time for this than feels reasonable. It is the least interesting stage and the one that decides whether an answer is possible at all.

DOCXTables and headers are easy to lose. Tracked changes may still be in there

This project reads the six formats directly in documents.py, using pypdf, python-docx and the standard library, with no loader framework. The CSV reader returns one section per row, and that single decision is the only reason "is Juneteenth a holiday" can be answered at all. It matters more than the choice of embedding model.

Chunking

Big enough to hold a whole answer, small enough not to dilute the match. 500 to 1000 tokens is the common range, with 10 to 15 percent overlap so a sentence split across a boundary still appears whole somewhere. Split on headings first and size second; splitting purely on character count cuts sentences in half.

This project uses LangChain's RecursiveCharacterTextSplitter at 700 characters with 80 of overlap. It tries paragraph breaks first, then line breaks, then sentences, and only cuts inside a word as a last resort. That splitter is the one framework dependency in the pipeline: reading the files is our own code, cutting the text is not.

Whatever you pick, the chunk has to carry where it came from. Title, section and document id travel with the text, or you cannot cite. A chunk size quoted without reference to your documents is a guess.

Embedding

Two rules that do not change. Questions and documents must be embedded by the same model at the same size. And changing either means rebuilding the whole index, which is a migration with a cost and a window, not a config tweak.

Dimension count is a storage and latency decision, not an accuracy dial you turn up for free.

The question that matters most is whether it filters inside the search. If it can only filter afterwards, you cannot do access control properly, for the reason set out earlier. After that: what it costs when idle, and whether it does hybrid search.

pgvector is genuinely fine up to a few million vectors. The reasons to leave it are hybrid search, sharding, and not wanting search traffic on your transactional database.

The chat model

Roughly seventy models have on-demand pricing on Bedrock in us-east-1: the Nova family, Claude, Llama, Mistral, DeepSeek, Qwen, Gemma and the GPT-OSS models. What actually narrows it down is rarely the benchmark score.

CheckWhy
Can you call it today, in this account and region?Anthropic models need a one-time use case form. That is a schedule risk, not a technical one
Does it support tool use?This whole design depends on it
Is the fallback from a different family?Two models from one vendor tend to be unavailable together
Does the fallback fit inside your timeout?Measured here: the SDK spent 15 of 29 seconds retrying before the fallback even started
Must the data stay in one geography?Use a regional inference profile (us., eu.) rather than global.

We tested Nova Lite as the primary model. It called the wrong tool and invented a citation, so it is good enough to degrade to and not good enough to lead with. Nova Pro costs 13 times more than Lite, so test whether the cheaper model handles your questions before assuming it cannot.

Putting it in Slack or Teams

It is wiring, not AI work.

The React app is one client of the API. Slack or Teams would be another. The retrieval, the access filter, the row-level security, the prompt and the model do not change. They sit behind the API and never knew which client was calling.

What you write is an adapter: receive the platform's webhook, verify its signature, map the sender to an employee, call POST /api/chat, and format the reply. That is ordinary application code, not AI work.

The part that needs care is the identity mapping. API Gateway trusts a Cognito token, and a Slack event gives you a Slack user id. Mapping one to the other must go through something verified, normally the email on the SSO account behind both. Match on a display name or a handle and you have put a spoofable field in front of salary data.
